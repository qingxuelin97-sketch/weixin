# specs/backfill.md — 离线回填 / 预调度通知（备份恢复见 specs/backup.md）

## 一、离线回填

### 为什么难

关掉 App 几小时后重开，世界应该像继续运转过。但 App 当时并没有在跑——这段历史只能在重开的
瞬间编出来，而两个方向翻车都很难看：

- **编多了**：回来面对 40 条没人信的未读，一眼假；
- **编错时间**：设定成夜猫子的朋友，早上六点给你发消息。

所以 `simulate()` 只负责决定「什么时候本该发生什么」：**不调 LLM、不碰存储、不读挂钟**，
是输入的纯函数。调用方把结果物化成 `fireAt` 在过去的 `scheduled_actions`，交给平时那个执行器
排空——实时与回填因此走同一条代码路径（宪法铁律 5），而不是第二套时间推进逻辑。

### 四条硬规则（都有单测钉住）

1. **窗口** = `(上次前台化屏障, now - 2min]`。屏障每次前台化落盘，绝不向屏障之前插入。
   末尾留 2min 余量，避免与正在播放的实时消息撞车。
2. **活跃时段**：时间戳必须落在人设 `activeHours` 内；交集为空就**沉默**。
   沉默不是退化行为——它本身才是最像真人的结果。
3. **限额**：≤3 人开口、每人 ≤2 条、帖 ≤6、每群每离线小时 ≤6 条、礼物 ≤1、
   社交提议（聚会+拉群）≤2；**双天花板** = `LIMITS.llmCalls`（真正要发网络请求的
   kind 才计账）+ `LIMITS.events`（总行数，免费 kind 也算）。>24h 只回填最近 24h。
4. **不得倒挂**：每条回填消息必须**晚于该会话的最后一条**。行是「现在」插入的，
   时间戳倒挂会直接破坏 `rowid 序 == 时间序`，而游标分页正依赖这个不变量
   （见 `specs/data-schema.md`）。

### 骨架先行

`runBackfill` 排完队就返回，正文交给常规 drain 生成。未读红点与会话预览立刻可见，不必等网络。
首次启动（无屏障）只落屏障、不编历史——给一个从没打开过的 App 伪造往事是荒唐的。
回填异常被吞掉，绝不阻塞启动。

### 确定性

种子 = `${seed}:${from}:${to}`，同一个离线窗口永远得到同一份计划。重开不重摇。

## 二、预调度通知

无服务器意味着：**能在 App 关闭时弹出的通知，必须在关闭之前就连正文一起排好**。
这一条约束推导出下面全部设计。

### 内容分级（`canPregenerateBody`）

| kind | 可预生成正文？ | 为什么 |
|---|---|---|
| `greeting` 早晚安 | ✅ | 锚定在时刻上，含义不依赖期间发生了什么 |
| `festival` 节日 | ✅ | 锚定在日期上 |
| `promise` 约定提醒 | ✅ | 锚定在约好的时刻上 |
| `followup` 追问 | ❌ | 引用近期对话；到点时对话可能早已走远，预览就是错的 |

`followup` 一律用微信原生的 **`[你收到一条消息]`** 无预览样式。

### 一致性铁律

通知展示过的正文**必须**原文入库、且 `createdAt === fireAt`。用户可能已经在锁屏上读过；
打开 App 却看到不同的文字、或同样的文字挂在不同时间，是最刺眼的一种穿帮。

### 平台

- 原生：`@capacitor/local-notifications`（已装 v7，对齐 Capacitor 7）。
- Web：浏览器无法为「没在运行的页面」排期，故 `scheduleNotifications` 在 Web 上返回 0，
  由返回值如实反映平台实际接受了几条——不谎报成功。无权限时静默 no-op。
- **真机锁屏验证需要 APK**（M5 构建范畴），本轮只保证代码路径就位。

每次回前台 `cancelAll()` 全量撤销重排：还挂着的通知是按用户已经走过的世界状态写的。

## M-I5 · 离线社交回填扩展

- **赞评离线可发生**：`SimInput.recentMoments`（离线前已存在的最新几条帖，
  由前台 pass 读入——simulate 保持纯函数）。预算 `LIMITS.socialReactions`（含
  赞与评，赞零 LLM 成本）；作者绝不自赞；反应时间恒晚于帖子时间；48h 以上
  的旧帖不再吸引反应。
- **AI↔AI 私信离线可发生**：每次离线至多 `LIMITS.offlineDms`（=1）场，配对取
  自共同群、种子化；<3h 的短离线不排（私聊需要时间差才可信）。事件**不带**
  群 convId——会话发生在隐藏私信线程，带了会误入群「≤2条/15分钟」限速账本
  （测试逮住过一次）。私信完成后的孵化（八卦外溢/joint_plan/agent_forward）
  经同一个 handler 自动发生。
- 物化 payload 与在线 handler 同形：赞评带 momentId，私信带 {a,b,groupId,fireAt}。

## M-I18 · 礼物与社交提议进入离线窗口

在此之前 `SimEvent` 只有 6 种 kind，后果是**这三件事在离线窗口里不可能发生**——
它们都由前台 pass 现摇，而前台 pass 的 `now` 是活钟，排出来的 `fireAt` 一律在未来：
缺席三天回来，那三天里她从没送过东西、群里没人提过聚会、没人提过拉群。
而且它们**完全不进离线预算的账**，等于绕过本轮要立的窗口闸。现补齐：

- **`ai_money`（礼物）**：决策仍然只有 `planGift` 一份（在线/离线同一个规划器）。
  离线只可能是 `treat`——生日/节日锚在「今天」，归前台；道歉/安慰要有你刚说的话可反应。
  `SimContact.gift = { affinity, lastGiftAt }` 由不纯的调用方解析（同 `SimGroup.activity`
  的安排）。注意 `runGift` 按设计**盖发送时刻的时间戳**而非 fireAt（rowid 序铁律），
  所以礼物是「在缺席里被决定、在你回来那一刻送到」。
- **`group_event` / `agent_invite`**：直接复用 `maybeGroupEvent` / `maybeGroupInvite`
  两个纯函数，只是把 `now` 换成窗口起点 `from`。`SimInput.groupRosters` 由调用方传入，
  与前台 pass 1.6 读的是同一份——「这三个人是不是已经在一个群里」不能有两个答案。
- **稳定 id 必须与在线路径一致**（`SimEvent.id`）：`gift_<conv>_<day>` /
  `gevt_<conv>_<week>_propose` / `ainv_<id>_<week>`。前台 pass 用 `actionExists` 守这三个
  id，回填若用自己的 `bf_…` id，同一件事会被排两次（enqueue 按 id upsert 的坑的反面）。
- **聚会提议就是群里的一条消息**，因此同样受「≤2 条/15 分钟」约束：与已排群消息
  撞窗口就跳过（不挤），本周的事件下次前台 pass 会用同一个 id 再排。
- **预算按重要度花，不按时间顺序花**：群闲聊数量比其他 kind 高一个数量级且集中在窗口
  开头，按时间截断等于把整个预算判给闲聊——实测连续 60 个种子都摇不出一次聚会。
  现按 `KEEP_ORDER` 花预算、按时间序返回。

## M-J1 · 离线回填也产记忆（`mem_extract` 进离线窗口）

在此之前，回填只造「发生过什么」，从不造「她记住了什么」：一夜群聊 20 条，第二天她
对其中任何一句都毫无印象——「她记得我们聊过的」只对用户亲眼看着发生的对话成立。现补齐：

- **规划规则**：回填窗口内某会话计划产出 **≥ `MEM_EXTRACT_MIN_NEW`（=6，与在线触发同一
  个常量，import 同源防漂移）** 条消息事件（heartbeat / group_msg / group_event 计数；
  agent_dm 发生在隐藏线程、赞评没有会话，均不计），则在**窗口尾**（`at = to`）排一次
  `mem_extract`。主语沿用在线约定（ChatPage）：单聊是联系人 id，群聊是会话 id 本身。
- **物化无特判**：payload 只带 `{contactId, convId, at}`——计划时消息还不存在，不可能有
  `uptoMsgId`。改由 `handleMemExtract` 在触发时刻解析边界（读该会话最新一条消息 id）；
  drain 按时间序执行，闲聊先落、抽取殿后，顺序由构造保证。
- **预算入账**：`LLM_COST.mem_extract = 1`（真实一次抽取调用），`KEEP_ORDER = 4`——
  记住一段热闹比它的第 20 句闲聊更重要，排在 group_msg 之前花预算。两表都是
  `Record<SimEvent['kind'], …>`，新 kind 不表态直接编译不过。
